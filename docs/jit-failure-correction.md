# 纠正：JIT 不可用的成因判断（2026-09-19 晚）

**本文纠正 `docs/jit-state-pollution.md` 的结论。**
那份文档把成因归为「同包名跑过 release 签名导致的状态污染」，
**该归因不完整**，不足以解释全部现象。

---

## 1. 反驳证据（决定性）

用**阶段 1 的最小探针**做隔离实验 —— 它只有 1.5MB，**完全不含模拟器代码**，
只有 `mmap(RW) → 写入 → mprotect(RX) → 执行` 这一件事。

同一台设备、同一时刻、同一个包名（`com.hps2.jitprobe`），debug 签名：

```
SELFCHECK_JSON={"available":false,"stage":3,
                "stageName":"mprotect(RX)","errno":22,
                "message":"系统当前拒绝将内存标记为可执行（JIT 被拦截）"}
```

**最小探针同样失败，错误与我方应用一字不差。**

=> **JIT 被拒与 Hps2 的代码无关。** 这是设备/系统层面的状态。

## 2. 我此前的推理错在哪

### 2.1 有过一次"卸载重装后恢复"，从而过度归因

时间线（今日）：

| 时刻 | uptime | 操作 | 结果 |
|---|---|---|---|
| 早先 | — | 装过 release 版（`normal_hap` 域）| — |
| 之后 | ~3 min | debug 版 | ❌ errno=22 |
| 然后 | — | 卸载 → 重装 | ✅ **可用** |
| 现在 | 1:19 | 卸载 → 重装 | ❌ **仍不可用** |

**卸载重装只成功过一次**，我却据此写了"根因是状态污染"。
**一次成功不足以确立因果** —— 这一次同操作已无效，说明那个推断站不住。

### 2.2 与阶段 1 的既有结论对照

`docs/jit-regression.md` 早已记录：

> JIT 可用性**不是设备的静态属性**，可能随运行期状态变化。
> 同一 HAP 文件：17:16 PASS → 19:14 FAIL（2 小时后）。

且探针自身给出的建议一直是：

> **请重启手机后重试。重启可恢复。**

**即：既有文档的结论（重启可恢复的运行期状态）比我的新归因更符合证据。**

## 3. 目前敢下的结论 vs 不敢下的

### 敢下（有证据）

- **JIT 可用性是运行期属性，会自行失效** —— 阶段 1 已实测，今日再次复现。
- **失效与本项目代码无关** —— 最小探针同样失败，错误一致。
- **失效时域是正确的** `o:r:debug_hap:s0`，签名/provision 也正确
  （`appProvisionType: debug`、`debug: true`）。
- **失效表现为 `mprotect` 加执行位被拒，errno=22 (EINVAL)**。

### 不敢下（证据不足）

- ❌ 不能说"根因是包名复用的状态污染" —— 已被本次实验反驳为不完整。
- ❌ 不能说"卸载重装可修复" —— 只成功过一次，第二次无效。
- ❌ 还不知道失效的**触发条件**（时间？次数？某个具体操作？）
- ❌ 还不知道 `mprotect` 为何被拒（是 XPM 还是别的机制）。

## 4. 下一步：把"触发条件"查清楚

需要控制的实验（**每次实验前重启设备**，只改一个变量）：

| # | 实验 | 目的 |
|---|---|---|
| 1 | 重启 → 立刻跑探针 | 建立基线（预期 PASS）|
| 2 | 重启 → 跑探针 → 启动 Hps2 → 再跑探针 | 判断是否被本应用影响 |
| 3 | 重启 → 跑探针 → 等 N 分钟 → 再跑探针 | 判断是否随时间失效 |
| 4 | 重启 → 跑探针 → 装 release 版 → 跑探针 | 判断 release 是否真的影响 |

**在此之前，不宣称任何归因成立。**

## 5. 对产品的影响（不变）

无论触发条件是什么，有一条是确定的：

> **GitHub 自签包必须能应对"JIT 运行期失效"** ——
> 因为用户也会遇到。因此应用的运行期 JIT 看门狗（`hps2_jitcheck`）
> 与明确的用户提示是**必需的**，不是可选的。

这一点在 `docs/distribution-strategy.md` 里已有设计（不降级 + 明确告知）。
