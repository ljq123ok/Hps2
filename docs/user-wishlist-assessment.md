## 专项：数据与存档外置（用户最强调的一条）

### 现状

```
ArkTS: dataRoot() = getContext(this).filesDir
                 = /data/storage/el2/base/haps/entry/files/   （应用私有沙箱）

native: EmuFolders::AppRoot = DataRoot = 上面那个路径
```

该目录下的内容：

```
bios/       用户选的 BIOS（被复制进来）
games/      游戏镜像（被复制进来）
sstates/    即时存档（.p2s + .backup）
memcards/   记忆卡（游戏内存档）  ← 路径为 DataRoot + "/memcards"
emulog.txt  核心日志
...
```

### 问题（与用户期待完全对应）

| 影响 | 说明 |
|---|---|
| **卸载即全部丢失** | BIOS、游戏、即时存档、**记忆卡存档**全在私有沙箱，卸载应用一并删除 |
| **用户不可见** | 普通文件管理器看不到，无法自行备份 |
| **更新风险** | 覆盖安装（`install -r`）通常保留沙箱，但卸载重装会清空 |

**尤其"记忆卡存档"** —— 那是用户在游戏里辛苦积累的进度，
比即时存档更重要，却也一样存在沙箱里。

### 用户建议的方案：放到 Download

```
Download/Hps2/
  bios/
  games/
  sstates/      即时存档
  memcards/     记忆卡（游戏内存档）
  logs/
```

**技术前提（早前已核实过一次）**：
要把数据放到用户可见目录，需要解决「应用如何长期读写该目录」的问题。
HarmonyOS 的做法是 `fileshare.persistPermission()` 持久化 URI 权限，
其要求的 `ohos.permission.FILE_ACCESS_PERSIST` 经查 SDK 的
`PermissionDefinitions.json` 为 `grantMode=system_grant`、
`availableLevel=normal` —— **系统自动授予、非受限、无需 ACL、无需弹窗**。
故技术上前提是成立的。

**但仍有未验证的部分**：
- 应用能否**直接枚举** Download/Hps2 下的内容（而非逐个文件授权）？
- 首次启动时该目录不存在，应用能否**自行创建**？
- 用户手动往里丢文件后，应用能否发现？

**这三点必须先做实验验证**，不能直接按"能"来设计。

## 建议的推进顺序

按「用户价值 ÷ 实现成本」排序：

### 🥇 第一：暂停菜单（成本最低，用户价值明确）
上游 `VMManager::SetPaused` 已可用，接一个按钮 + 状态显示即可。
**注意**：暂停/恢复与 VM 线程的交互，我们已在读档中踩过坑
（`SetPaused(true)` 会立即改状态但 VM 线程未必真停），
需要复用已建好的 `Hps2Sync::RunOnVmThread` 机制。

### 🥈 第二：数据与存档外置（用户最强调，但需先验证）
先做可行性实验（上面三点），再设计目录结构与迁移逻辑。
**迁移**必须考虑：已有用户的沙箱数据要能搬到新位置，不能丢。

### 🥉 第三：游戏本体识别（成本低）
首页显示当前游戏的 serial / CRC / 名称。
底层 API 已在用（即时存档取 serial 组文件名），只需暴露到 UI。

### 第四：图形设置完善 / 屏幕按键自定义（成本较高）
- 图形设置需要逐个核实每个选项在本项目（GLES/OHOS）下是否真的生效
- 按键自定义需要可拖拽编辑 UI + 布局持久化

## 对这个反馈本身的态度

用户明确说"不催促，能做多少做多少"，
且提出的方向都**与项目自然演进一致**（不是天马行空的需求）。
其中「数据外置」这一条**尤其值得优先** —— 因为它是**数据安全问题**：
用户现在的游戏进度在卸载或重装应用时**会全部丢失**，
这不是"功能缺失"，而是**可能造成实际损失**的风险。
