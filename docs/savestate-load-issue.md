# 读档后无法正常游戏 —— 诊断结果

**日期**：2026-09-22
**状态**：🔴 已定位现象与直接原因，**根因待确认**（需进一步实验）

---

## 1. 现象（用户反馈 + 日志证据）

用户反馈："读取存档不闪退了，但不能正常游戏"。

**日志证据（决定性）**：

```
LOAD step1/2/3 全通过
HPS2_SAVE: loadState(1) ok=1          ← 读档本身成功

MONITOR: ee_pc=0x0022186c frame=495   ← 读档前，PC 在变化
MONITOR: ee_pc=0x8000fe74 frame=675   ← 读档后
MONITOR: ee_pc=0x8000fe74 frame=855   ← **完全相同的 PC**
```

**关键**：`frame` 持续增长（875 → 855），但 `ee_pc` **停在同一个值不动**。

=> EE 卡住了。帧在推进但 CPU 不前进 —— 正是"不能正常游戏"。

## 2. 直接原因：读档后 EE 立即触发异常并卡死

emulog 明确记录：

```
[29.1381] EE ARM64: Entering recompiled code (pc=0x0010FF9C)
[29.1384] TLB Miss, pc=0x10ffa8 addr=0xe0000330 [load]
[29.1399] TLB Miss, pc=0x1101f0 addr=0x40 [store]
[29.1399] Trap exception at 0x004f4804      ← EE 陷入异常
[29.1760] OSD [LoadStateFromSlot]: Loaded state from slot 1.
```

而卡住后的 `ee_pc = 0x8000fe74`：

```
0x8000FE74 & 0x1FFFFFFF = 0x0000FE74   （约 64KB 处，KSEG0 低地址）
```

**这是 EE 的异常向量区**：Trap 异常后 CPU 跳入异常处理程序，
然后**卡在那里**（PC 不再变化）。

## 3. 时间线上的一个疑点

`Trap exception` 的时间戳（29.1399）与 `Loaded state`（29.1760）
**非常接近**，说明异常几乎是与读档同时发生的 —— 而非玩了一会儿才出问题。

另注：读档前 PC 是 `0x0010FF9C`（低地址，不寻常），
读档后一度变为 `0x0022186c`（正常游戏代码区），随后跳到异常向量。
**这一串跳转本身值得进一步查证。**

## 4. 尚不能确定的（不臆测）

| 待确认 | 说明 |
|---|---|
| **根因** | 是存档数据与当前 build 不兼容？还是恢复流程缺步骤？|
| TLB Miss 是原因还是症状 | 两者都可能，需实验区分 |
| 与 4KB 页覆盖是否相关 | 本项目用 `OVERRIDE_HOST_PAGE_SIZE=0x1000`，而存档可能记录页相关状态 |

## 5. 下一步实验（按成本排序）

### 实验 A：同一 build 内存档再读（最低成本，优先）
```
在**当前 build** 下：启动游戏 → 存档 → 继续玩一会 → 读档
```
- 若正常 ⇒ 问题是**存档与 build 不匹配**（旧档不可读，属预期）
- 若仍卡死 ⇒ 是恢复流程本身的问题

**动机**：现有存档是 12:23 与 12:30 生成的，而此后我重装过多个
新 build（含布局、悬浮球、配色等改动）。虽然这些改动主要在 ArkTS 侧，
但**必须先排除"旧档不兼容"这个最简单的解释**。

### 实验 B：对比"读档后"与"正常运行时"的 TLB 状态
若 A 仍失败，在 `PostLoadPrep()` 前后打印 TLB 表项数，
确认 `MapTLB` 是否真的恢复了映射。

### 实验 C：临时禁用 fastmem 后读档
若禁用 fastmem 后能正常，则问题在 fastmem 映射恢复。

## 6. 对用户的影响与建议

在根因确认前：

- **不建议依赖即时存档的可靠性** —— 可能出现"读档后卡死"。
- 存档文件本身写入正常（`sstates/` 下有 `.p2s` 与 `.backup`），
  数据没丢，问题在读取后的状态恢复。

**这是本功能的已知缺陷，会继续排查。**
