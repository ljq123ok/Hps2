# JIT 不可用的第三种成因：包名复用导致的状态污染

**日期**：2026-09-19
**严重性**：🟡 中 —— 现象与既有记录混淆，容易误判

---

## 1. 现象

自签版（`debug_hap` 域）JIT 突然不可用：

```
SELinux 域 : o:r:debug_hap:s0:x68,x335,x512,x868,x1024   ← 域正确
JIT 状态   : 不可用
诊断       : 阶段=mprotect-rx errno=22 (EINVAL)
```

**域正确、provision 类型是 `debug`、`debug: true`** —— 一切看起来都对，
但 `mprotect` 加执行位被拒。

## 2. 排查过程与误判

### 2.1 首次误判：以为是阶段 1 的回归

阶段 1 记录过同症状（`docs/jit-regression.md`），当时**重启设备后恢复**。
于是先检查设备是否刚重启：

```
up 3 min, 0 users, load average: 12.32, 27.19, 10.98
```

设备**确实 3 分钟前刚重启**，但 JIT 仍不可用。
=> 排除了"重启即可恢复"这一路径，说明**不是**阶段 1 那个现象。

### 2.2 二次误判：怀疑域字符串变化

```
阶段1 (PASS) : o:r:debug_hap:s0:x53,x335,x512,x868,x1024
当前  (FAIL) : o:r:debug_hap:s0:x68,x335,x512,x868,x1024
```

`x53` 与 `x68` 不同，一度怀疑是域差异。

**但这是误读**：该字段是 SELinux 的 categories 集合，
每次进程实例分配都可能不同（同一时期 `normal_hap` 实例也是 `x68`）。
**与 JIT 权限无关。**

### 2.3 真正根因

回顾本次会话对**同一包名** `com.hps2.jitprobe` 的操作序列：

| 顺序 | 操作 | 运行域 |
|---|---|---|
| 1 | 装 release 签名版（`app_gallery` Profile）| 装不上 |
| 2 | 装「指定设备发布」版（`internaltesting`）| **`normal_hap`** |
| 3 | 卸载，装回 debug 签名版 | 应为 `debug_hap` |

**第 2 步让系统为该 bundle 记录了"无 JIT 权限"的状态**，
卸载重装后仍残留 —— 导致第 3 步的 debug 版拿不到 JIT。

## 3. 解法（已验证）

**卸载后重新安装**（不需要重启设备）：

```bash
hdc uninstall com.hps2.jitprobe
hdc install -r hps2-debugsigned.hap
```

验证结果：

```
JIT 状态 : 可用
           已通过「申请 → 写入 → 提交可执行 → 执行并校验」完整往返
```

## 4. 对项目的三个影响

### 4.1 与阶段 1 回归的区别

现在已知**两种**"JIT 不可用"：

| | 阶段 1 回归 | 本次（状态污染）|
|---|---|---|
| 触发 | 未知（运行期状态变化）| 同包名跑过 `normal_hap` 域 |
| 域 | `debug_hap`（正确）| `debug_hap`（正确）|
| 重启设备 | ✅ 可恢复 | ❌ **无效** |
| 卸载重装 | 未测试 | ✅ **有效** |

**两者症状相同**（`mprotect` errno=22），但**处置手段不同**。
排查时必须两条都试。

### 4.2 对用户的支持文档

README 的"JIT 不可用怎么办"需要补充这一条：

> 若你**曾用不同签名安装过同一包名**（例如先装过商店版），
> 需要**完全卸载**后再安装自签版，重启设备无效。

### 4.3 对产品形态的印证

这进一步说明**双包必须用不同的 bundleName**。

若商店版与自签版共用一个包名，用户从商店版切换到自签版时
**会踩到这个状态污染**，且症状（JIT 不可用）极具误导性 ——
用户会以为自签版没用，实际只需卸载重装。

**建议**：商店版使用独立包名（如 `com.hps2.store`），
或在应用内检测并提示用户"请完全卸载后重装"。
