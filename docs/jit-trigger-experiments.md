# JIT 失效触发条件 —— 受控实验设计

**背景**：多次观测到「JIT 突然不可用，重启后恢复」，但**触发条件未知**。
此前我曾误归因为"包名复用的状态污染"，已被实验反驳
（见 `docs/jit-failure-correction.md`）。

**原则**：每次实验前**重启设备**建立干净基线，**只改一个变量**。

---

## 已知事实（有证据）

| 项 | 观测 |
|---|---|
| 症状 | `mprotect` 加执行位被拒，errno=22 (EINVAL) |
| 域 | `o:r:debug_hap:s0`（正确，与成功时同为 x68 类别）|
| 签名 | `appProvisionType: debug`、`debug: true`（正确）|
| 隔离实验 | **最小探针（1.5MB，无模拟器代码）同样失败** ⇒ 与本项目代码无关 |
| 恢复 | **重启设备**（已验证 2 次：阶段 1 一次、今日一次）|

## 观测到的时间线（今日，用于生成假设）

| 时刻 | uptime | 事件 | JIT |
|---|---|---|---|
| ~13:05 | 1:19 | 装 debug 版 | ❌ |
| 13:07 | — | 卸载 → 重装 | ❌ **无效** |
| 13:08 | — | 装最小探针 | ❌ |
| **15:09** | **1:33**（重启后）| 装 Hps2 | ✅ **可用** |

> 注：13:05-13:08 期间 uptime 是 1:19（即约 11:50 开机），
> 而 15:09 的 uptime 是 1:33（约 13:36 开机）—— 与用户"已重启"一致。

## 待验假设（按优先级）

### H1：失效与「连续安装/卸载同一 bundle」相关

**依据**：今日失败前，我在短时间内对 `com.hps2.jitprobe` 做过多次
安装/卸载/换签名（debug → release → internaltesting → debug）。

**实验 1**：
```
重启 → 跑探针（记录基线，预期 PASS）
     → 连续安装/卸载 5 次探针（不启动）
     → 再跑探针
```
- 若 FAIL ⇒ 与安装次数/频率相关
- 若 PASS ⇒ 排除

### H2：失效与「进程启动次数」或「运行时长」相关

**依据**：阶段 1 的回归是「同一 HAP 文件 2 小时后失效」。

**实验 2**：
```
重启 → 跑探针（基线）
     → 每 15 分钟跑一次，连续 2 小时
     → 记录首次 FAIL 的时刻
```
- 能定位"存活窗口"长度

### H3：失效与「启动过 VM（大量匿名可执行内存）」相关

**依据**：只有 Hps2 会申请数百 MB 的 JIT 内存；而最小探针只申请几页。
若失效前运行过 VM，可能是内存/资源策略被触发。

**实验 3**：
```
重启 → 跑探针（基线）
     → 启动 Hps2 并跑一个游戏 5 分钟
     → 停止 → 再跑探针
```
- 若 FAIL ⇒ 与"启动过 VM"相关（这对产品很关键：意味着**用户玩过一次后可能就失效**）

### H4：失效与「release 签名安装」相关（我此前的主张，已被削弱但未彻底排除）

**实验 4**：
```
重启 → 跑探针（基线）
     → 装 release 签名版（internaltesting Profile）
     → 卸载 → 装回 debug 版
     → 跑探针
```

### H5：失效与「设备资源压力」相关

**依据**：曾观测到 JIT 内存分配失败（`Failed to allocate code memory`，
当时 MemFree 仅 220MB）。JIT 申请需要连续大块内存。

**实验 5**：
```
重启 → 跑探针（基线）
     → 制造内存压力（开大应用/反复启动大型应用）
     → 再跑探针
```

---

## 执行顺序

先做 **实验 3**（H3）—— 理由：
- 若成立，**对产品影响最大**（用户玩一次就可能失效，必须有应对）
- 实验成本低（我已能自动启动 Hps2）

其次 **实验 2**（H2），因为它能给出"存活窗口"，指导用户与我们的测试节奏。

